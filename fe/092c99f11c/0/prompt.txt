## Part A — Visualization

### 1. What `residual view` and `residual serve` render

**Delivery.**
- `view` writes a self-contained `landscape.html` to a temp dir or `--out` and prints the path (`src/view/mod.rs:69`).
- `serve` binds `127.0.0.1:8787` with `tiny_http` and serves `/` (the HTML) and `/snapshot.json` (`src/view/mod.rs:28,98`).
- Neither command mutates the ledger (`src/view/mod.rs:1-6`).

**Page structure.** `src/view/shell.html` has three collapsible `&lt;details class="card"&gt;` sections:
- `data-view="matrix"` (`:683`): a server-rendered force × component table.
- `data-view="landscape"` (`:690`): the D3 views, chosen with a segmented control.
- `data-view="modify"` (`:741`): forms for staging edits.

**Three landscape views** (`web/src/nkp-landscape.ts:1-12`). All three read the same page-wide filters: visible forces, visible components, fission threshold.
- **bundle** (`nkp-bundle.ts:1-14`):
  - Radial hierarchical edge bundling (Holten 2006). The hierarchy is root → attractor → component.
  - Components sit on a circle in per-attractor arcs.
  - Component–component coupling edges are routed through the hierarchy with `d3.curveBundle`. The bundling-tension slider defaults to 0.85.
  - Edge width and opacity scale with the shared-force count (`bundleEdgeStyle`, `:328`).
  - Min-shared-forces and top-N "tiers" sliders prune weak couplings.
- **heatmap** (`nkp-seriation.ts:1-14`):
  - Component × component matrix. Off-diagonal cells are the count of forces the two components share. The diagonal is each component's K (its total force count).
  - Rows and columns are reordered by average-linkage clustering on cosine-normalised coupling, with leaf orientation (`seriate`, `:83`). Tightly coupled components form diagonal blocks.
- **regions** (`nkp-hypergraph.ts:1-7`, `createRegionsView :965`). This is the main work on this branch.
  - It is a bipartite force↔component graph with one edge per membership, not a clique expansion.
  - Attractors are not nodes. Each is a translucent region around its force nodes.
  - Overlapping regions show components sitting between attractors.

**Node and edge encoding** (`nkp-graph.ts`):
- Components are circles when `actual` and squares when `proposed` (`:~195`).
- Stressors are diamonds and purposes are lighter circles (`nkp-hypergraph.ts:~690-700`, `forceGlyphPath`).
- Colour is a hash-derived HSL per attractor (`attractorColors`, `:412`). A component takes a muted version of its dominant attractor's colour.
- A dotted ring marks a fission candidate (a component with more forces than the threshold, `:204,222`).
- Coupling edges are solid. A dotted fusion edge joins components with identical force vectors (`:300-310`).
- Out-of-focus items are dimmed to 0.5 opacity.

**Regions layout** (`docs/dual-ring-mini-pyramid-plan.md:24-30`), radial from the centre outward:
1. Purpose ring of per-attractor mini-pyramids, apex inward.
2. Inner annulus.
3. Component band, a fixed 3 hops thick.
4. Outer annulus.
5. Stressor ring of mini-pyramids, apex outward.

- Each attractor splits into a purpose pyramid and a stressor pyramid of the same colour (`plan:34-39`).
- One convex hull covers all of an attractor's forces and is painted below the components. Neighbouring pyramids sit with no gap.
- Pyramid growth is tall before wide: 1 → 2 → 2:1 → 3:1 → 3:2 → 3:2:1 … (`miniPyramidLayersForCount`, `landscape-triangular-lattice.ts:260`; plan `:41-49`).
- Each layer of a pyramid is a sub-shape. Forces are assigned to layers by similarity.
- Components are seeded on their dominant attractor's ray, in the middle of the band.
- Everything snaps to a "curved sprocket" polar lattice (`axialToDualRingPixel :778`, `pixelToDualRingAxial :795`, `nearestFreeDualRingCell :866`). Every node type shares one lattice pitch of 60px (`nkp-hypergraph.ts:406,651`).
- The "ergodic core zone" is drawn as dashed rings. Forces stay outside it and components stay inside (`:414-417`).

**Bundling inside regions** (`plan:57-63`):
- Purpose edges route component → inner-annulus midpoint → layer approach → force.
- Stressor edges use the outer annulus instead.
- A "long arc" is used only when the direct route would enter the wrong annulus. It leaves on a tangent to the correct annulus, within ±10°.
- Idle bundle opacity is half the lit opacity (`REGIONS_BUNDLE_IDLE_OPACITY`, `nkp-hypergraph.ts:713`).

**Physics.** A d3 force simulation (`:2038-2049`) combines:
- zero-charge components,
- weak link forces (`REGIONS_LINK_STRENGTH = 0.1125`),
- attractor cohesion toward the centroid (`createAttractorCohesionForce`, `:~600`),
- pairwise force interaction with strength 7 and range 220 (`:705-707`),
- collision at the lattice pitch,
- 50 synchronous settle ticks (`INITIAL_SETTLE_TICKS`, `:598`).

An optional "keep simulating physics" toggle holds alphaTarget at 0.05.

**Interaction:**
- **Selection.** There is one cross-view key space: `component:&lt;name&gt;`, `force:&lt;key&gt;`, `attractor:&lt;id&gt;` (`landscape-selection.ts:1-12`). Click toggles selection, double-click clears it, and a sidebar shows entity details.
- **Highlighting.** It is partial-transitive, not a full closure (`shell.html:~735`). A selected attractor lights its forces and every component those forces touch. A selected force lights its components, its attractor and sibling forces. A selected component lights the attractors of forces that touch it and every force under those attractors.
- **Dimming.** Non-lit items drop to 0.12 opacity, with a 0.24 "semi" ring one hop out.
- **Drag.** Dragging a region moves the whole attractor group (`nkp-hypergraph.ts:2496-2540`). With lock on (the default), the group drops back to canonical pyramid placement, and unlocking allows repositioning that is still lattice-snapped.
- **Other controls.** Zoom is pinch or ctrl+scroll at 0.6× d3's default speed. There are also pan, reset view, lattice and attractor-name toggles, and a focus-component dropdown.
- **Staged edits.** The page never writes to the ledger.
  - `model.ts` keeps a `PendingState` of adds, updates and toggles layered over the snapshot.
  - `toCommandLines` (`:314`) turns it into ordered `residual add/update` commands.
  - The page offers a copy textarea (`forms.ts`), a downloadable bash script that begins with `residual write authorize` (`export-script.ts`), and an import modal that parses pasted commands back in.
  - After each change, `landscape.sync()` redraws all views.
  - `web/generated/cli-schema.json` (from `scripts/gen-cli-schema.sh`) is the ground truth for which fields are required.

### 3. Ideas that generalize to code architecture graphs

1. **One shared selection key space with partial-transitive highlighting** (`landscape-selection.ts`). `module:`, `file:`, `symbol:` and `group:` keys would work across every view and the sidebar. Lighting only the entities relevant to the question, rather than the full closure, avoids "everything lights up" on dense graphs.
2. **Several linked views over one pure model.** The same `buildNkpGraphModel` feeds three views: bundle, seriated heatmap and regions. For diffcore, a bundle view is the overview, a seriated matrix is the dependency-clustering audit, and a bipartite view fits change-group ↔ file.
3. **Radial hierarchical edge bundling** (`nkp-bundle.ts`). Modules → files → symbols maps directly onto Holten's directory hierarchy. Bundling lets many import edges share paths. The tension slider, min-weight slider and top-N tiers keep it readable.
4. **Seriation instead of alphabetical order.** The average-linkage ordering with a leaf-flip step (`nkp-seriation.ts:83`) turns a matrix into visible blocks, which suggests natural module boundaries.
5. **Bipartite membership graph instead of clique expansion.** Group nodes and member nodes joined by membership edges. Overlapping translucent hulls show elements that belong to more than one group. This fits change groups and files that appear in several groups.
6. **Grid-snapped layout** (60px pitch, one lattice for every node type). A fixed pitch gives uniform spacing and removes force-layout jitter. Sorting items into rings or bands (purpose / component / stressor) encodes role by position, so colour is free for the group.
7. **Encoding discipline.** Shape for kind (circle/square/diamond), colour for group, dotted outline for a flagged state, opacity for focus. The thresholds are explicit constants (dim 0.12, semi 0.24, idle 0.225).
8. **Locked-by-default placement with unlock to drag.** This gives a stable mental map, and layout does not drift as data updates.
9. **Page-wide filters feed every view.** Controls carry `data-landscape-for="bundle heatmap"` and are hidden when not relevant to the active view (`shell.html:700-730`, `controlAppliesTo`).
10. **The read-only page stages commands, and the CLI remains the single writer.** `toCommandLines` produces an ordered, validated script. Reviewer actions in diffcore could use the same pattern.

The dual-ring pyramid machinery is NKP-specific (purposes versus stressors). For architecture graphs the radial stack is a template: role-banded rings with a hull per group.

Caveats for adoption: SVG performance was not examined, and `nkp-hypergraph.ts` is a 3003-line monolith. The branch history shows heavy iteration on layout (more than 20 commits), so the geometry is still churning.

## Part B — Integrity and NFR enforcement

### 4. Mechanics

**`residual verify`** (`src/verification/mod.rs`, `src/verify.rs`). Verification policy lives in storage-config, not in a separate config module.
- `verify outcomes` (alias `traits`): each outcome must be at least three words (subject verb predicate). It must also contain at least one word from the lexicon (`verify.rs:97-165`).
- `verify links`: attractor ids must resolve, and shortnames are required (`:166`).
- `verify all`: runs both, then prints tag warnings. Dangling `@stressor:`/`@purpose:`/`@component:` tags are warnings, not blockers (`:85`). It also checks defense-ledger isolation (`:65`).
- A slow-verify warning fires at 2s or more, because slow verification "may drive hook bypass" (`verify.rs:8-18`).
- `check_one_way_tags`: a tag may be missing from metadata, but a tag in code that is missing from metadata fails (`verification/mod.rs:100`).
- `check_personas_adequacy`: at least 2 personas (`:128`).
- The walk-reminder cadence is non-blocking and prints to stderr (`:55`).

**Git hooks** (`residual generate hook`, `src/verification/git_hook.rs`):
- Three hooks are installed: pre-commit, commit-msg and post-commit.
- Each hook is a marked block, `# &gt;&gt;&gt; residual:&lt;name&gt; &gt;&gt;&gt;` … `# &lt;&lt;&lt; … &lt;&lt;&lt;` (`:85-118`). Foreign hook content is preserved and a reinstall replaces the residual block in place. The shebang is forced to `/bin/sh` for nix sandboxes (`:123-130`).
- pre-commit (`:14-44`):
  - Refuses to commit if the write-authorization marker is staged.
  - Refuses to commit if any `residual/` path other than `config.toml` is staged. The comment says there is no override flag by design.
  - Runs `verify all` and the walk reminder.
  - Weakness: the "strict" gate parses `residual config | grep strict | awk` (`:38`), which is brittle.
- commit-msg: `residual verify commit-msg "$1" --staged` (`:47`).
- post-commit: `residual branch sync-commit &gt;/dev/null 2&gt;&amp;1 || true`, so it never fails a commit (`:53`).

**Commit-msg enforcement** (`commit_msg.rs`). README cites Scoped Commits (`README.md:202`).
- Conventional-Commit prefixes such as `feat:` and `fix(scope):` are rejected outright (`:106-110,146-158`).
- A `general - ` prefix is always allowed (`:112`).
- `&lt;component&gt;: S-12: summary` or `P-nn` is allowed only if the component and force id exist (`:116-128,160`).
- Under `super_strict`, only those two forms pass (`:130`).
- Otherwise the subject must contain a component or lexicon term (`:136`).
- Staged paths are matched against component names to emit hints (`:188,240+`).
- Enforcement is opt-in: `commit_msg_enforce` defaults to false, so the hook warns (`storage/config.rs:24`, `git_hook.rs:65`).
- `commit template` and `suggest_subjects` generate valid subjects from the ledger (`:203,~237`).
- Body lines are never validated.

**Write authorization** (`src/storage/write_authorization.rs`):
- `residual write authorize` writes `residual/.residual-write-authorized` containing `expires_at=&lt;rfc3339&gt;` (default 30 minutes, `:10-33`).
- `require` is enforced only when the sidecar is enabled. It is a time-boxed, human-granted gate against agents mutating metadata (`:35-64`).
- The marker is not git-ignored on purpose, so a staged marker is caught by pre-commit (`:17-19`). `.gitignore` does ignore `residual/.residual-write-authorized`, which sits oddly beside that comment.

**Change-detection hashes and sessions** (`src/storage/integrity/sessions.rs`):
- `.storage-hashes` holds a per-file `path=hash` snapshot (`:11,125-136`). On a mutation, drift (changed, added or removed files) blocks it unless `--force` is passed (`begin_mutation`, `:~213`).
- A `.session.lock` with pid and timestamp (30s TTL) serializes mutation (`:9-50`).
- The hash is `DefaultHasher` (SipHash, `:107`). Rust documents that the algorithm may change between releases, so the snapshot is not durable. A fixed digest would be a straightforward improvement.

**Git-sidecar branch storage** (`src/storage/git_sidecar.rs`):
- Metadata lives on an orphan branch (default `residual/metadata`). Code stays on the working branch.
- All writes go through git plumbing (`hash-object`, scratch index, `write-tree`, `commit-tree`, `update-ref`). The working tree and HEAD are never touched (`:1-8`).
- `config.toml` can live in the parent directory (stealth mode, `ConfigHost::Parent`).
- `branch_mode` gives per-code-branch metadata branches via a pattern (`:30-35`). `branch edit`, `save`, `merge` and `sync-commit` manage them.
- The working-tree policy is `warn`, `block` or `ignore` for staged `residual/` paths (`:805-840`).
- Verify and the viewer read from the sidecar tip (`metadata_dir`).

**General-purpose, portable ideas:**
- Marked-block hook merging.
- A commit-subject grammar validated against a project vocabulary (component registry plus scopes), with hints derived from staged paths.
- Time-boxed write authorization.
- Hash-snapshot drift detection.
- A plumbing-only sidecar branch.
- A one-way tag rule.
- A slow-verify warning.
- A warn-by-default, opt-in enforcement dial.
- Policy stored in a single config.
- Hard blocks with no override flag for leakage.

## Part 1: How T3 Code models projects, threads and worktrees

T3 Code is MIT-licensed with about 24k stars. It is a pnpm monorepo: `apps/{server,web,desktop,mobile,marketing}` and `packages/{contracts,client-runtime,shared,effect-acp,...}`. The server is TypeScript on Effect.

### Vocabulary
These definitions come from `docs/internals/glossary.md`.
- **Environment**: one running server plus the machine, credentials, workspace access and state it owns.
- **Project**: an environment-local record rooted at a directory (the workspace root).
- **Thread**: the durable conversation and work history for a project. It outlives provider process exits.
- **Turn / run**: one user-to-agent cycle.
- **Worktree**: a separate git checkout that a thread can use instead of the project's main checkout.
- **Session**: the provider runtime attached to a thread. It can stop and resume without deleting the thread.
- **Checkpoint**: a saved workspace state used for diffs and restore, stored as a hidden git ref.

### Where state lives
State is in a per-user "T3 home" (`~/.t3`), never in the user's repo. The path layout is in `apps/server/src/config.ts` (`deriveServerPaths`, lines ~130-160):

- `~/.t3/userdata/` holds the SQLite database (`statev2.sqlite` at HEAD), `settings.json`, `keybindings.json`, `attachments/`, `logs/`, `secrets/`, `themes/`, `environment-id` and `server-runtime.json`.
- `~/.t3/worktrees/&lt;repoName&gt;/&lt;sanitizedBranch&gt;` holds worktrees. The path is built in `apps/server/src/vcs/GitVcsDriverCore.ts:3194`.
- `~/.t3/caches/` holds provider status caches.
- `~/.t3/scratch/&lt;date&gt;-&lt;slug&gt;-&lt;id&gt;` holds the folders for threads with no project. `ManagedProjectFolders.ts` also makes `~/.t3/projects/&lt;slug&gt;` for projects started from a name only (new git repo, README, first commit).
- `~/.t3/dev/` is a separate state dir used in dev mode.
- `server-runtime.json` records `{pid, host, port, origin, startedAt}`. Locally it shows `127.0.0.1:3773`.

The one thing that touches the repo's git data is checkpoints. They use hidden refs under `refs/t3/checkpoints` (`apps/server/src/checkpointing/Utils.ts:4`), so no commits land on the user's branch. `docs/internals/overview.md` says this explicitly.

### Persistence is event-sourced, with projections
- **Source of truth**: an append-only event log. `docs/internals/overview.md` says "The event log is the source of truth for orchestration state."
- **Local DB (older v1 layout)**: the installed `state.sqlite` is 1.5 GB. It has `orchestration_events`, `orchestration_command_receipts`, `projection_projects`, `projection_threads`, `projection_thread_messages`, `projection_thread_activities`, `projection_turns`, `projection_thread_sessions`, `projection_pending_approvals`, `projection_thread_proposed_plans`, `projection_thread_pull_requests`, `checkpoint_diff_blobs`, `provider_session_runtime`, `projection_state`, `effect_sql_migrations`, `auth_sessions`, `auth_pairing_links` and `pull_request_files_viewed`.
- **Local row counts**: 30 projects, 336 threads, 313,937 events.
- **Local event mix**: most events are `thread.activity-appended` (184k), `thread.meta-updated` (55k), `thread.message-sent` (45k) and `thread.session-set` (24k). There are 336 `thread.created` and 30 `project.created`.
- **Event table columns** (`orchestration_events`): `sequence` (autoincrement), `event_id`, `aggregate_kind`, `stream_id`, `stream_version` (unique per stream), `event_type`, `occurred_at`, `command_id`, `causation_event_id`, `correlation_id`, `actor_kind`, `payload_json` and `metadata_json`.
- **Project row**: `projection_projects(project_id, title, workspace_root, scripts_json, default_model_selection_json, default_thread_env_mode, favicon_path, auto_pull, deleted_at, ...)`. It is plain path plus metadata, with soft delete (`deleted_at`) and an index on `(workspace_root, deleted_at)`.
- **Thread row**: `projection_threads(thread_id, project_id, title, branch, worktree_path, latest_turn_id, runtime_mode, interaction_mode, model_selection_json, archived_at, pinned_at, pin_order_key, ...)`. A worktree is just a `branch` and `worktree_path` column on the thread.
- **v2 at HEAD**: migration `055_OrchestrationV2.ts` adds `orchestration_v2_events`, `orchestration_v2_command_receipts` and about 15 `orchestration_v2_projection_*` tables. These cover threads, runs, run_attempts, nodes, provider_sessions, messages, plans, checkpoints and context_handoffs.
- **Write path**, from `docs/internals/overview.md` and `apps/server/src/orchestration-v2/`:
  - `Orchestrator.ts` serializes commands and decides events with no I/O.
  - `EventSink.ts` commits events, projections, the command receipt and outbox effects in one DB transaction.
  - Subscribers see events only after commit.
  - `EffectWorker.ts` runs side effects (start a provider turn, capture a checkpoint) after commit and feeds results back as commands.
  - `CommandReceiptStore.ts` makes retries idempotent.
  - A command ack means the intent committed, not that the work finished.
- **Rule worth noting**: persisted events must stay decodable on replay, so schema changes must account for stored history.

### How a project is added
- **RPC methods**: `projects.add`, `projects.list`, `projects.remove`, `projects.mutate`, `projects.createNew` and `projects.ensureScratch`. Browsing is `filesystem.browse`. All are in `WS_METHODS` in `packages/contracts/src/rpc.ts:338`.
- **Command path**: adding a project creates a `project.create` command with `{projectId, title, workspaceRoot, scripts}` (`apps/server/src/orchestration-v2/ProjectCommands.ts`).
- **Duplicate guard**: `ProjectWorkspaceConflictError` stops two live projects sharing a `workspaceRoot`.
- **Folder picker**: the server owns the filesystem, so the web client picks a folder through server-side `filesystem.browse`. This works remotely, and the desktop app can also use a native dialog.
- **Project-level settings** (`docs/user/project-settings.md`) are stored on the owning server as overrides layered over environment defaults, over built-in defaults.

### Threads and worktrees in the UI
- **New thread**: it can use the project's main checkout or **New worktree**. "New thread in this worktree" is also available (`docs/user/thread-sidebar.md`).
- **Worktree branch names**: the default prefix is `t3code/`, and a model can generate the name.
- **Multi-model fan-out**: Shift-click several models and each gets its own thread and worktree.
- **Sidebar**: threads are grouped under projects. Threads can be pinned, reordered by `pin_order_key`, archived, snoozed and "settled". Settlement is server-owned and driven by PR merge or inactivity.
- **No-project threads**: they get a scratch folder.
- **Sidebar code**: `apps/web/src/components/` has `Sidebar.logic.ts`, `Sidebar.drag.ts` and a `sidebar/` folder. I did not read these in depth.

### Server to client
- **Transport**: a WebSocket at `GET /ws` (`apps/server/src/ws.ts:3729`), speaking Effect RPC (`effect/unstable/rpc`).
- **Contract**: `packages/contracts/src/rpc.ts` is the schema-first contract, about 180 methods. Subscriptions stream only the state a client needs, so one open thread does not pay for every thread's history.
- **Version guard**: an orchestration protocol version is checked on connect. A mismatch returns HTTP 426.
- **Auth**: `auth_sessions` and `auth_pairing_links` tables. "Authentication of a socket does not authorize every method on it."
- **Client logic**: shared connection and domain state is in `packages/client-runtime`. Web, desktop and mobile only supply platform services and UI.
- **Capability flags**: clients negotiate features through an environment descriptor, not client version (for example `threadPullRequests`).

### Patterns worth copying for diffcore
1. **User-level store, repo untouched.** A project is `{id, title, workspace_root}` in one SQLite DB under a per-user dir (use `dirs::data_dir()/diffcore`). Everything else (analysis cache, worktrees, attachments) lives beside it. T3 puts nothing in the repo except hidden git refs.
2. **Soft-deleted project rows** with a unique-live-root guard on canonicalized path.
3. **Event log plus projections.** This is heavy for diffcore. A lighter version is `projects`, `review_sessions` and `analysis_runs` tables, plus an `events` table only if live streaming or undo is wanted. If the full thing is adopted, copy the single-transaction (events + projection + receipt) commit.
4. **Command ids with receipts** make client retries idempotent.
5. **Thread = durable unit of work.** For diffcore, a "review session" would be project + base ref + head ref + worktree path + analysis snapshot. Worktrees go in `~/.local/share/diffcore/worktrees/&lt;repo&gt;/&lt;branch&gt;`, created by the server rather than the UI.
6. **Server owns filesystem and git.** The UI sends a path and `filesystem.browse` requests, and never touches the disk.
7. **Single multiplexed socket with an explicit method table and a protocol-version handshake.** A Rust equivalent would be axum WebSocket plus serde-tagged request/response enums, or SSE for subscriptions. Typed TS bindings could come from `specta` or `ts-rs`.
8. **`server-runtime.json`** (pid, port, origin) lets CLIs and other tools discover a running server.
9. **Hidden refs** (`refs/diffcore/...`) are a good place to pin analyzed commits.
10. **Server-owned derived state.** Clients render persisted results and do not derive them from their own clocks.

T3 also has `apps/server/src/review/ReviewService.ts` with `review.getDiffPreview` and `review.getDiffFileContents`. It is a plain git diff preview, so there is no semantic review to compare against.

Caveat: the T3 repo moves fast (4.6k commits). The installed local DB is the older v1 schema, while HEAD has v2.

## Part 2: `sem`

The installed binary is **sem 0.7.0**, but upstream is **0.26.0** (released 2026-10-02). Upstream is Ataraxy-Labs/sem, about 3.4k stars, 662 commits, active daily, dual licensed MIT OR Apache-2.0. The installed version is about 19 minor versions behind. Upgrade before relying on it. The newer commands `sem find`, `sem callers`, `sem refs` and `sem grep`, the `sem_callers` MCP tool and `entities --signatures` do not exist in 0.7.0.

### Workspace crates
`sem-core` (library on crates.io, also used by `weave` and `inspect`), `sem-cli`, `sem-mcp` (built on `rmcp = "1"`), `sem-plugin` and `sem-cloud-client`. `sem-core/src` has `differ.rs`, `graph.rs`, `context.rs`, `hotspot.rs`, `import_resolution.rs`, `scope_resolve.rs`, `session.rs` and `test_detect.rs`. It parses with tree-sitter and git2, and hashes with xxhash. README claims 32 languages. There are also non-code plugins (JSON, YAML, TOML, Markdown, CSV, Svelte, Vue, ERB, LaTeX), plus a chunk-based fallback for unsupported files.

### Runs against `/home/v0id/Documents/repos/diff-core` (sem 0.7.0)
- **`sem diff HEAD~1 HEAD`** gives entity-level output per file. `Cargo.lock` is chunked as `∆ chunk lines 881-900`, which is noise, so filter with `--file-exts .rs .ts`. Filtered output looked like this:
  - `⊕ function analyze_repo [added]`
  - `∆ function app_router [modified]`
  - `⊕ module analyze [added]`
- **Output formats**: `--format terminal|plain|json|markdown` and `--json`. `--no-cosmetics` hides whitespace and comment-only changes. `--stdin` takes `FileChange[]` JSON and `--patch` takes a unified diff.
- **JSON shape**: `{changes:[...], summary:{added, deleted, modified, moved, renamed, reordered, orphan, fileCount, total}}`. Each change has `entityId` (e.g. `crates/diffcore-server/src/analyze.rs::function::analyze_repo`), `entityName`, `entityType`, `changeType`, `filePath`, `startLine`/`endLine`, `beforeContent`/`afterContent` and `structuralChange`. Module-level code appears as an `orphan` entity.
- **`sem impact app_router --file ... [--json]`** lists direct dependencies, direct dependents and transitive impact ("14 entities transitively affected (depth 2)"). It also supports `--tests`, `--deps`, `--dependents` and `--depth`.
  - **Accuracy caveat**: it listed `EmbeddingCache::new` and `::get` as dependencies of `app_router`, which looks like name-only matching (false positives). Check whether 0.26.0 fixes this. The changelog mentions improved resolution for Dart and TypeScript.
- **`sem graph --json`** (add `--file-exts .rs`) returned `{edges, entities, stats}`: 3,700 entities and 10,151 edges for diff-core.
- **`sem blame &lt;file&gt;`** gives per-entity last author, commit and date. **`sem log &lt;entity&gt; --file ...`** shows an entity's history ("added", then "modified (logic)").
- **`sem context &lt;entity&gt; --budget N`** returns a token-budgeted bundle of the target plus its dependencies.
- **`sem verify --diff`** checks call arity against signature changes. It reported "ok: No broken callers".
- **`sem entities &lt;path&gt;`** lists entities with line ranges.
- **`sem mcp`** is a stdio MCP server. Upstream 0.26 exposes tools such as `sem_entities`, `sem_diff`, `sem_blame`, `sem_impact`, `sem_context` and `sem_callers`.
- **Cache**: SQLite outside the repo (`SEM_CACHE_DIR` overrides it). Telemetry is local-only unless opted in, and `SEM_NO_TELEMETRY=1` disables recording.

### Existing diffcore link
Only a worktree at `.claude/worktrees/sem-entity-diffing/crates/diffcore-tauri/Cargo.toml:11` references `sem-core` (git rev `a971ece5...`, features `parallel`, `grammar-all`). The main workspace `crates/*/Cargo.toml` has no `sem-core` dependency. So diffcore does not currently depend on sem on the branch I looked at.

### What diffcore could lean on
1. **Entity-level changes as the review unit.** `sem-core`'s differ replaces file-level or chunk-level diff for code. It gives rename and move detection and structural (cosmetic vs logic) classification. Use `--no-cosmetics` or the classification to demote noise.
2. **Dependency graph and impact.** `graph` and `impact` could drive the diffcore graph and "story arc" ordering: review callees before callers, and list affected tests.
3. **Blame and log per entity**: "who touched this function and why", which fits a review aid.
4. **`context --budget`** for building LLM prompts for summaries.
5. **`verify --diff`** for a cheap "this signature change breaks N callers" check.
6. **Hotspot and test-detection modules** in `sem-core`: `hotspot.rs`, `test_detect.rs`.
7. **`Ataraxy-Labs/inspect`** is an existing entity-level review tool. It scores each changed entity 0.0 to 1.0 on classification, blast radius, dependent count and API exposure, and it untangles tangled commits with union-find. It has a CLI with JSON output and an MCP server with 6 tools. Its license is in LICENSE.md and I did not read it. It overlaps diffcore's goal and could be a source of ideas, or a dependency.
8. **Integration choice**: use the library (`sem-core` on crates.io, pinned) for in-process speed, or shell out to `sem ... --json` for loose coupling. Shelling out is easy but costs a process per call, and the version drift above shows the CLI can lag.

## Part 3: MCP in Rust

**Recommended crate: `rmcp`**, the official Rust SDK at github.com/modelcontextprotocol/rust-sdk. About 4k stars, Apache-2.0. crates.io shows **3.5.0, released 2026-09-28**, with frequent releases (3.4.1 on 09-23, 3.4.0 on 09-15). The README says it supports protocol versions `2025-11-25` and `2026-07-28`. It is tokio-based and covers tools, resources, prompts and tasks. It has proc macros for tool and prompt generation, plus client and server roles. The sem repo pins `rmcp = "1"`, so pin deliberately.

**Transports**, from feature flags in `crates/rmcp/Cargo.toml`:
- stdio: `transport-io`, via `server` plus `transport-io`.
- child-process client: `transport-child-process`.
- Streamable HTTP server: `transport-streamable-http-server`, plus `transport-streamable-http-server-session` for stateful sessions with `LocalSessionManager`.
- Streamable HTTP client: `transport-streamable-http-client` and `-client-reqwest`.
- Custom async read/write: `transport-async-rw`.

**One axum process can host both the web UI and an MCP endpoint.** `StreamableHttpService` is a Tower service, and the SDK's own example (`examples/servers/src/counter_streamhttp.rs`) mounts it on an axum router:
```rust
let service = StreamableHttpService::new(
    || Ok(Counter::new()),
    LocalSessionManager::default().into(),
    StreamableHttpServerConfig::default().with_cancellation_token(ct.child_token()),
);
let router = axum::Router::new().nest_service("/mcp", service);
```
For diffcore, `.nest_service("/mcp", service)` goes on the same `Router` that serves `/api/*` and the SPA. The cancellation token ties MCP shutdown to `with_graceful_shutdown`. The server config has `allowed_hosts` for DNS-rebinding protection, with a `localhost`/`127.0.0.1` list in its docs. It also has an `Origin` allowlist, which is empty by default and disables origin validation. A local review server should set both and bind to loopback.

T3 Code does the same thing with its own stack. `apps/server/src/mcp/McpHttpServer.ts` serves MCP on `/mcp` in the same server process as `/ws`. Its toolkits (`worktree/`, `project/`, `thread/`, `pullRequests/`, `preview/` and others) expose project, thread and worktree operations to agents. A diffcore MCP server could expose the same kind of tools (`list_projects`, `get_review_session`, `get_entity_impact`, `add_review_comment`) over the shared state.

## 1. Summary

- **Cheapest win: reuse `sem-core`'s entity graph.** diffcore already depends on sem. sem-core (0.26.0, published 2026-10-02) ships `parser/graph.rs`: an `EntityGraph` with `Calls`, `TypeRef` and `Imports` edges at entity granularity. It also has `impact`, `context`, `callers` and `refs` features and an mmap-able query index. I read the file's public API and the README, but I did not run it.
- **Best precision upgrade: SCIP, as an opt-in tier.** Compiler-grade definitions and references from `rust-analyzer`, `scip-typescript` and others, read through the `scip` Rust crate. SCIP has no call edges, so diffcore would derive them.
- **Most tools in the "code knowledge graph for agents" wave are not safe to depend on.** GitNexus is PolyForm Noncommercial. Others duplicate what diffcore and sem already do. The useful things to take from them are Leiden community detection, entry-point flow tracing and blast-radius scoring. Port those ideas and don't take a dependency.
- **Dead ends:** stack-graphs, GitHub `semantic`, Sourcetrail, CodeQL (license), Glean and Joern.
- **For the D3 side:** `elkjs` for layered and compound layouts, `d3-hierarchy` for the module overview, and a hand-written DSM and edge bundling with core D3. Avoid WebCola.

## 2. Candidate comparison

Columns: what it does, runtime, license, 2025–26 status, and Rust integration mode. Where it matters I note language coverage, graph granularity and fit for "explain a diff".

### Code indexing and graph

**sem / sem-core (Ataraxy-Labs)**
- Entity-level diff (rename, move and structural-hash detection), plus `impact`, `context`, `callers`, `refs`, `graph --json` and an MCP server.
- Rust, with tree-sitter. License is MIT OR Apache-2.0 per README and crate; the GitHub API reports Apache-2.0.
- Very active: sem-core 0.26.0 on 2026-10-02, about 3.4k stars, last push 2026-10-03.
- Integration is a crate dependency (already in use) or the CLI's `--json` output.
- Covers about 28–32 languages. Granularity is entity (function, class, method, type), with call, type-reference and import edges.
- Fit: high. It is the same tree-sitter foundation diffcore uses, and the diff and the graph are consistent with each other.
- Risks:
  - The API moves fast. The README I fetched said 0.23.1 while crates.io says 0.26.0, so pin the version.
  - sem advertises a "cloud" mode and local-only telemetry counters (README). Verify nothing leaks when used as a library.
  - Edge resolution is heuristic (scope and import resolution, no type checker). Expect misses on dynamic dispatch.
- Sources: https://github.com/ataraxy-labs/sem, https://docs.rs/sem-core/latest/sem_core/, https://github.com/Ataraxy-Labs/sem/blob/main/crates/sem-core/src/parser/graph.rs

**SCIP (Sourcegraph, now `scip-code`)**
- A protobuf index format of documents, occurrences, symbols and relationships, produced by per-language indexers that use real compiler front-ends.
- Apache-2.0. The `scip` crate is 0.10.0 (2026-09-03) with about 2.7M downloads. The repo moved to `scip-code/scip`. Sourcegraph announced open governance in March 2026, with a steering committee including Uber and Meta engineers.
- Indexers: rust-analyzer (`rust-analyzer scip`), scip-typescript (JS/TS), scip-java (Java/Scala/Kotlin), scip-go, scip-python, scip-clang, scip-ruby, scip-dotnet, scip-php and scip-dart. I confirmed scip-typescript, scip-java, scip-go and scip-dart were pushed within the last week; I did not check the others.
- Integration: run the indexer as a subprocess, then parse the `.scip` file with the `scip` crate.
- Granularity is precise symbol definitions and references with roles. The spec has no call-graph edges (confirmed in `docs/scip.md`). You would build `calls` by mapping reference occurrences to the enclosing definition. I believe `enclosing_range` is available on occurrences, but I have not verified it.
- Fit: medium to high as an optional precision layer. It is poor as the default, because indexers often need a working build or `node_modules`, are slow, and cover each language separately.
- Sources: https://github.com/scip-code/scip, https://lib.rs/crates/scip, https://sourcegraph.com/blog/the-future-of-scip, https://github.com/scip-code/scip/blob/main/docs/scip.md

## 3. Ranked recommendation

### 1. Adopt `sem-core`'s `EntityGraph` as the primary entity-edge source

**Why:**
- It is already a dependency, with the same tree-sitter basis.
- It gives entity-granular call, type-reference and import edges, plus `callers`, `refs`, `impact` and `context`.
- It has an on-disk index, so cold lookups are cheap.
- It is actively maintained, with permissive licensing, and it keeps the diff (entity IDs) and the graph consistent.

**Plan:**
- Keep diffcore's file-level graph, entrypoint detection and flow grouping (the unique value), but source symbol-level edges from sem-core instead of maintaining parallel resolvers for languages where sem is good.
- Expose sem's edge list through the same MCP and JSON surface.

**Risks:**
- The API churns quickly, so pin it and wrap it in an adapter.
- Edge-resolution quality is heuristic.
- Check telemetry and cloud code paths when used as a library.
- Overlap with diffcore's existing graph needs a clear ownership line.
- Run a quick benchmark on 3–5 real 50–100 file AI-generated diffs before removing anything.

### 2. Add SCIP ingestion as an optional "precise" tier

**Why:**
- It gives compiler-accurate definitions and references for Rust (rust-analyzer), TS/JS, Java/Kotlin/Scala, Go, Python, C/C++ and others.
- It is vendor-neutral, with open governance since March 2026, and the `scip` crate is maintained.
- It can verify or upgrade edges sem found heuristically.

**Plan:**
- Add `diffcore index --scip` to run the language's indexer. Merge occurrences into the graph as `references` edges, and add `calls` edges by attributing each reference to its enclosing definition.
- Use SCIP symbols as stable IDs for cross-run comparison.

**Risks:**
- Indexers need a working project environment and are slow. Failures must degrade gracefully to tier 1.
- No call-edge semantics, so diffcore owns the derivation logic.
- Mapping SCIP symbols to sem entity IDs is non-trivial. Match by file and range.
- Per-language indexer quality varies.

### 3. Port ideas from code-review-graph and GitNexus (do not depend on them)

**What to take:**
- Leiden community detection to refine flow groups.
- Execution-flow tracing from entry points with depth and branching limits.
- Surprise scoring for cross-community edges ("this change couples two unrelated areas").
- Edge-confidence labels (EXTRACTED vs INFERRED), which would help human reviewers decide what to trust.
- Aider-style PageRank to order the "start here" list.

**Why:**
- code-review-graph is MIT, so its design is a safe reference.
- GitNexus is PolyForm Noncommercial, so read its README for ideas only and copy no code.
- For Leiden in Rust, I did not verify any crate. Check for a maintained implementation before writing your own.

**Alternative or complement:** `codebase-memory-mcp` (MIT, single static binary) as an optional external-index subprocess. I put it below the above because of overlap and unverified claims.

**Not recommended:** stack-graphs, Joern, CodeQL, Glean, Sourcetrail, GumTree (unless you want edit scripts), and the LLM-diagram tools.

### (1) Module and package overview

- **Base view.** Use an icicle or treemap from `d3-hierarchy` over the directory tree. Color by change density (entities added, modified or deleted from sem), and size by LOC or entity count.
  - A treemap packs well for 100+ files.
  - An icicle preserves hierarchy better for labels.
  - This is the CodeCharta idea.
- **Coupling view.** Use a DSM (dependency structure matrix) built by hand with D3 scales. Order rows by cluster, then by directory. It scales to hundreds of modules and shows cycles and layering violations clearly. Highlight cells that include changed edges.
- **Edge overlay.** Use hierarchical edge bundling (`d3.cluster` plus `d3.lineRadial` with `curveBundle`) only for the changed subset of cross-module edges. Bundling all edges produces hairballs.
- **Package dependency view.** Use ELK layered with compound nodes (package contains modules) for a call-flow-style diagram.

### (2) Changed-symbol neighborhood

- **Subgraph.** Take 1–2 hops of callers and callees (the `sem context` and `callers` semantics) around each changed entity. Cap it at roughly 50–100 nodes, with "+N more" collapse nodes.
- **Layout.** Use ELK layered with direction RIGHT: callers on the left, the changed entity in the middle, callees on the right. This reads as data flow, and layered layouts are more legible than force layouts for call DAGs.
- **Exploratory mode.** Offer a `d3-force` ego layout as a toggle, with a pinned center node, `forceCollide`, and link distance tied to edge type.
- **Encoding.** Use fill for change kind (added, modified, deleted, moved), a border for confidence (compiler-verified vs heuristic), and dashed lines for inferred edges.
- **Avoid** WebCola for this. It is dormant, and ELK handles the same constraints with better ports and compound support.

### (3) Change-group flow

- **Layout.** Use ELK layered with compound nodes. Each flow group is a container with its changed files or entities inside. Entry points sit on the left, and the layered layout orders groups along the call or data direction. This also serves as the swimlane view PR-Lens-style tools use.
- **Aggregate view.** Use `d3-sankey` between groups (width equals the number of cross-group edges). It requires a DAG, so condense strongly connected components first. A chord diagram (`d3-chord`) is an alternative for dense group-to-group coupling, but it is harder to read than Sankey.
- **Reading order.** Add a numbered "suggested review order" overlay from a topological sort of groups. Rank within a group using PageRank or fan-in.
- **Arc diagram** (linear file order with arcs) works as a small, cheap view for showing which files within one group depend on each other.

### Angular notes

- Run ELK in a Web Worker and cache layouts by graph hash.
- Render with D3 into SVG for fewer than about 2k elements. Use Canvas for larger graphs.
- If a pure-Rust layered layout is desired for server-side use or for the MCP server, I did not find or verify a maintained ELK-equivalent crate. Check `rust-sugiyama` or similar before relying on one.

## Five most important findings

1. **The shipped pipeline only understands 3 languages.** `ast::parse_file` (`ast/mod.rs:212-261`) has hand-written extractors for TS/JS, Python and Go. For every other language it returns an empty `ParsedFile` (no definitions, imports or calls). That covers Rust, Java, C#, PHP, Ruby, Kotlin, Swift, C/C++, Scala and the 23 extras. The CLI (`diffcore-cli/src/main.rs:401,550`), the server (`diffcore-server/src/analyze.rs:92`) and `eval/repos.rs:~438` all call `pipeline::parse_files_parallel`, which wraps that function. The declarative `.scm` QueryEngine path (`query_engine.rs`, `languages/*`, `queries/`) handles all 36 languages. In production it is never used to build the graph, entrypoints or clusters. For non-TS/JS/Py/Go repos, groups therefore fall back to directory heuristics.
2. **The documented "primary" IR pipeline is dead code in production.** `pipeline.rs:1-18` says the flow is QueryEngine → IrFile → `build_from_ir` → `detect_entrypoints_ir`. Outside tests, `build_from_ir` and `detect_entrypoints_ir` are never called. In `diffcore-cli/src/main.rs:552-560` the CLI runs `parse_all_to_ir` and discards the result (`_ir_files`). It does this only to warm `.diffcore/cache/ir/`, which it never reads for analysis (up to 100 MB of JSON written into the target repo). `detect_entrypoints_ir` converts back to `ParsedFile` (`entrypoint/mod.rs:27`). The eval harness is inconsistent too. Synthetic fixtures use `engine.parse_file` (the QueryEngine, `eval/fixtures.rs:~172`). Repo evals use the legacy path (`eval/repos.rs`). Eval scores for the synthetic fixtures therefore do not measure what ships.
3. **The graph only contains changed files.** Every entry point builds `file_inputs` from `diff_result.files` only (`main.rs:386-400`). Imports to unchanged files can't resolve. Entrypoints that weren't edited are never detected. Flow groups are effectively "connected components among changed files", not true flows. There is no repo-wide graph and no impact analysis.
4. **The orchestration is copy-pasted four times.** The parse, graph, entrypoints, flow, cluster, rank sequence appears in `run_analyze_and_return` (`main.rs:339`), in `run_analyze` (`main.rs:470`), in `diffcore-server/src/analyze.rs`, and in `eval/fixtures.rs` and `eval/repos.rs`. There is no `core::analyze()` function. The copies already differ: the IR cache warm-up, the refinement-config handling and the cache-check conditions. The ranking inputs are hard-coded in the CLI: `centrality: 0.5` for all groups (25% of the weight, so it does nothing), `has_db_migration` passed as `false`, and `uncertainty` as 0.1 or 0.5.
5. **sem-core is not in the Rust workspace any more.** It was only in the deleted `diffcore-tauri` crate (`crates/diffcore-tauri/src/commands/mod.rs:865-925` at `ccb657b^`, dependency pinned to rev `a971ece5` in that crate's Cargo.toml). ## 2. Data pipeline: git refs to output

**Stages (CLI `run_analyze`, `main.rs:470-675`):**
1. `Repository::discover`, then `DiffcoreConfig::load_with_global_llm_from_dir`.
2. `extract_diff` (`main.rs:677`) produces `git::DiffResult { files: Vec&lt;FileDiff{old/new_content, hunks, additions, deletions}&gt;, base_sha, head_sha }`. The default base is `detect_default_branch`, else "main". `include_uncommitted` defaults to true.
3. Cache check (`cache::compute_cache_key`) returns the stored `AnalysisOutput` on a hit.
4. Ignore filtering (`config.is_ignored`), then `parse_files_parallel` produces `Vec&lt;ParsedFile&gt;` (legacy extractors).
5. `build_workspace_map` and `SymbolGraph::build_with_workspace` produce the `SymbolGraph`.
6. `detect_entrypoints` produces `Vec&lt;Entrypoint&gt;`. `analyze_data_flow` and `enrich_graph` add heuristic Reads/Writes/Emits/Handles edges.
7. `cluster_files(graph, entrypoints, changed_files)` produces `ClusterResult { groups: Vec&lt;FlowGroup&gt;, infrastructure }`.
8. Ranking: `compute_group_risk_flags` (path substring checks), `rank_groups` produces `RankedGroup`.
9. `build_analysis_output` produces `AnalysisOutput { version "1.0.0", diff_source, summary, groups, infrastructure_group, annotations: Option&lt;Value&gt; }`.
10. `store_cached` (this is the pre-LLM result).
11. Optional LLM refinement (`run_refinement`, which rewrites `groups` and `infrastructure_group`) and annotation (`run_annotation`, Pass 1 overview only, stored as an untyped `serde_json::Value`).
12. JSON written to stdout or `--output`.

**Persistence in the target repo:**
- `.diffcore/cache/&lt;sha256&gt;.json` holds the final output.
- `.diffcore/cache/ir/&lt;sha&gt;.json` holds IR files (write-only in practice).
- `.diffcore/&lt;ctxslug&gt;--N/{session,comments,analysis}.json` holds sessions.
- Nothing adds `.diffcore/` to `.gitignore`. The docs say "gitignored by convention" (`cache.rs:12`).
- `.diffcore/groups.json` is not written by core or cli. `export-groups` writes wherever `-o` points, and `ReviewSession.groups_manifest_path` records it.
- Global state is `~/.diffcore/config.toml` and `~/.diffcore/cache/refinements/`. Overrides: `DIFFCORE_CONFIG_HOME`, `DIFFCORE_REFINEMENT_CACHE_DIR`.

## 3. State management and brittleness

- **Stale analysis cache (bug).** `compute_cache_key` hashes the schema version, `base_sha`, `head_sha` and sorted paths only (`cache.rs:31-52`). The default CLI mode (`include_uncommitted=true`) uses `diff_branch_to_workdir`, which sets `head_sha: None` (`git.rs:~262`). The CLI only uses the mtime-aware `compute_cache_key_working_dir` for `--staged` and `--unstaged` (`main.rs:~368`). Editing a file in the default mode, with the same file list and base, returns the old analysis. The key also ignores config (ignore globs, ranking weights, layers) and the diffcore version beyond a manual `CACHE_SCHEMA_VERSION = "2"`.
- **Cache vs. LLM inconsistency.** The cache stores pre-refinement output. A cache hit returns early (`main.rs:~540`) unless `--annotate/--refine*` is passed. Refinement defaults to enabled (`RefinementConfig::default().enabled = true`, `config.rs:182-190`). The first run is refined and later runs return unrefined cached output.
- **Config test writes to the real global config.** `config.rs:1388-1407` sets `DIFFCORE_GLOBAL_CONFIG_DIR`, but the code reads `DIFFCORE_CONFIG_HOME` (`config.rs:513`). `save_global()` therefore writes the user's actual `~/.diffcore/config.toml` during `cargo test`. `set_var` also races with parallel tests.
- **Hard-coded layout and framework assumptions:**
  - `cluster/mod.rs:264-335` has special `fixtures/` handling (`semantic_fixture_root`, `is_semantic_fixture_*`). That is eval-corpus overfitting in production code.
  - `LARGE_DIFF_PARTITION_THRESHOLD` is "intentionally gated so it does not perturb the eval corpus" (`mod.rs:~54`).
  - `entrypoint/mod.rs:277-296` hard-codes Next.js `app/` and `pages/`. `flow/mod.rs:866-900` hard-codes Next.js detection.
  - `build_workspace_map` handles only JS monorepos and defaults to `src/index.ts` (`graph/mod.rs:~590`).
  - `rank.rs:95-117` uses substring checks. `contains("auth")` flags "author.ts", `contains("acl")` flags "oracle", `contains("schema")` flags any schema-named file.
  - Export/import-groups default `--base main` (`main.rs:~223,~241`).
- **Global mutable state** is minimal: `OnceLock` for engines and automata, and thread-local parser pools. This is not a problem.
- **Count mismatch.** `summary.total_files_changed` is `diff_result.files.len()` including ignored files such as `.diffcore/` (`output.rs:~103`). Groups only include non-ignored files.
- **Dead output fields.** `FileChange.symbols_changed` is always `vec![]` in production (`rescue.rs:463`, `manifest.rs:119`; nothing fills it). `EdgeType::Instantiates` is never emitted.

## 4. sem integration

- **Current state:** absent from core, cli and server. Evidence: a grep for `sem_core|sem-core` in `*.rs`/`Cargo.toml` across `crates/` returns nothing, and `Cargo.lock` has no `sem-core`. It lived in `crates/diffcore-tauri` (deleted in `ccb657b`). `PLAN.md:18` still describes it as a git dependency.
- **How it was wired:** `get_sem_entities` (at `ccb657b^:crates/diffcore-tauri/src/commands/mod.rs:896`) maps cached `diffcore_core::git::FileDiff` to `sem_core::git::types::FileChange { file_path, old_file_path, status, before_content, after_content }`. `Copied` maps to `Modified`. It then calls `compute_semantic_diff(&amp;file_changes, &amp;create_default_registry(), None, None)` on a blocking thread and returns `Vec&lt;SemanticChange&gt;`. It is stateless, reuses the in-memory diff, and needs no repo access.
- **What sem provides** (checked at `~/.cargo/git/checkouts/sem-72016dc394781fc0/a971ece/crates/sem-core`):
  - `SemanticChange { entity_id, change_type (added/modified/deleted/moved/renamed/reordered), entity_type, entity_name, parent_name, start/end_line, old_start/end_line, file_path, old_file_path, before_content, after_content, … }`.
  - A `DiffResult` with counts.
  - Plugins for code (many grammars), markdown, json, yaml, toml, csv, vue, svelte and erb.
- **Important for the rework:** sem-core also ships an `EntityGraph` (`parser/graph.rs`, 2819 lines). It has entities keyed by id with `parent_id` and line ranges, edges `Calls`, `TypeRef` and `Imports`, forward and reverse indexes, `impact_analysis_bounded`, `build_incremental` and `from_parts` for caching. It also has `scope_resolve.rs` (3351 lines), `import_resolution.rs` and `hotspot.rs`. This overlaps diffcore's `SymbolGraph` and is better placed for entity-level views and for graphs that include unchanged files. I did not evaluate its accuracy. Guess: it can replace diffcore's call/import edge extraction and fix findings 1 to 3 at once.
- **Gap:** `AnalysisOutput` carries no entity data. Groups are file-level (`FileChange`) and `symbols_changed` is empty. Entities are not linked to flow groups.

## 5. Graph

- **Nodes** (`graph/mod.rs:19-27`): `id = "file"` for a Module node (one per file, `SymbolKind::Module`) and `"file::name"` for each definition. Kinds are Function, Class, Struct, Interface, TypeAlias, Constant and Module. Definitions are top-level by name only. Methods get ids from `Definition.name` (qualification is language-dependent) and have no parent link. Duplicate ids are silently skipped (`mod.rs:~120`).
- **Edges:** `GraphEdge { edge_type }` only (`mod.rs:32-35`). There is no weight, line number, count, confidence or resolution quality. Kinds actually produced:
  - `Imports`: always from the importing file's Module node to a symbol or module.
  - `Calls`: caller symbol to callee, resolved by name through the import map. There is no scope or type resolution. Method calls resolve only if the receiver is an imported name.
  - `Extends`.
  - `Reads/Writes/Emits/Handles`: heuristic edges from a symbol to its own file's Module node (`flow/mod.rs:826-862`). These are self-referential markers, not real edges to resources.
- **What reaches the output:** the `SymbolGraph` is not serialized into `AnalysisOutput` (a `SerializableGraph` exists but is only used for roundtrip tests). Each `FlowGroup` gets `edges: Vec&lt;FlowEdge{from,to,edge_type}&gt;`, only the edges where both endpoint files are in the same group (`bfs.rs:78-97`). Cross-group edges are dropped, and `to` and `from` are symbol ids.
- **Is it enough for interactive graph views?** No, not as shipped. File-level views would have to be derived by projecting symbol ids from the group edges. Missing pieces:
  1. Cross-group and cross-file edges.
  2. Module (directory) hierarchy.
  3. Nodes for unchanged context.
  4. Edge multiplicity, call sites and line info.
  5. A "changed" flag per symbol.
  6. Parent/child (class→method) containment.
  Symbol granularity is also unreliable outside TS/JS/Py/Go (finding 1).
- **Performance guess:** `collect_import_edges`/`collect_call_edges` rebuild `known_paths: Vec&lt;&amp;str&gt;` for every file and `resolve_import_path` scans it linearly, which is O(n²).

## 6. LLM layer

- **Providers** (`llm/mod.rs:582-620,753-835`): HTTP providers Anthropic, OpenAI, Gemini, OpenRouter and GitHub Copilot, plus subprocess providers `claude` (`claude --print --output-format stream-json --json-schema …`, `claude_cli.rs:~66`) and `codex` (`codex exec --sandbox read-only`, `codex_cli.rs:~80`). Aliases are mapped in `canonical_provider_name`. The trait covers `annotate_overview` (Pass 1), `annotate_group` (Pass 2), `evaluate_quality` (judge) and `refine_groups`. The CLI uses only Pass 1 and refinement. Pass 2 is not wired.
- **Key resolution** (`resolve_api_key`, `mod.rs:639`): `key_cmd`, then the `key` config field (plaintext), then `DIFFCORE_API_KEY`, then a provider env var. With no provider configured, it picks "anthropic" if any key env var exists, else `detect_default_provider`, which prefers an authenticated Codex CLI, then Claude CLI, then Anthropic API (`mod.rs:839`).
- **key_cmd trust boundary:**
  - `apply_global_llm_defaults` (`config.rs:~455-510`) forces `key_cmd` and `refinement.key_cmd` to the global config's values. A repo-local `key_cmd` is discarded with a warning. This is tested (`config.rs:1411,1438`).
  - `execute_key_cmd` validates against a blocklist of `` ` $ | ; &amp; &lt; &gt; \n \r `` and then runs `sh -c`. The blocklist is weak but only matters for the global config.
  - **Gap:** the repo-local `.diffcore.toml` still controls `llm.provider`, `llm.model` and `llm.key` (plaintext), and the repo workdir is passed to the CLI providers. A hostile repo can select `codex` or `claude`. They run inside the repo (`current_dir`/`-C`) with the diff and file contents in the prompt. Prompt injection from repo content reaches an agent with read tools. Claude's CLI is launched with no tool restrictions; only the prompt says "Do not modify files" (`claude_cli.rs:17-21`). Codex does use `--sandbox read-only`.
- **9router is half-done.** `nine_router_base_url` exists in config and `openai_compatible_base_url()` (`mod.rs:738`) returns it. Nothing outside tests calls it, and all providers hard-code their URLs (`anthropic.rs:23`, `openai.rs:23`, …). `run_refinement` also builds a fresh `LlmConfig` with `..Default::default()`, dropping the base URL (`main.rs:~758`).
- **Refinement is on by default**, so every `analyze` tries an LLM call (and may launch the Claude or Codex CLI, with a warn-and-continue fallback) unless disabled in config.
- **Pass 1 sends no code.** It sends only file lists, an edge summary and counts (`main.rs:828-870`).
- **VCR** (`llm/vcr.rs`, 1047 lines, `VcrMode::{Record,Replay,Auto}`) is a decorator keyed by (provider, model, request hash, prompt-template hash). It is used only in tests (`tests/vcr_integration.rs`, `adversarial_refinement.rs`), never in production code.

## 7. Architectural flaws (top 10, with evidence)

1. **Two parallel extraction stacks** (`ast/` legacy vs `query_engine`/`languages`/`ir`). Production uses the one that supports 3 languages. Findings 1 and 2 above.
2. **Pipeline orchestration lives in the CLI binary and is duplicated** (`main.rs:339` vs `:470`, plus server and eval). The cli `main.rs` is 1875 lines, including `run_launch`, `run_embed_diff`, `write_output` and eval commands. Core exposes no `analyze(repo, opts) -&gt; AnalysisOutput`.
3. **Duplicated graph and flow code.** `graph/mod.rs` has legacy and IR versions of each collector. `flow` has `analyze_data_flow` and `analyze_data_flow_ir`. `entrypoint` has an IR shim. `output.rs` and the CLI both compute diff stats and risk flags.
4. **Graph scope and edge poverty** (changed files only, edges carry only a type, heuristic edges point at self), so it is not usable for the planned interactive views.
5. **Hard-coded frameworks and path heuristics.** `entrypoint/mod.rs` is 2335 lines of per-framework string matching. `cluster/classify.rs` and `rank.rs` use path-substring rules. Eval-fixture special cases live in production clustering (`cluster/mod.rs:264-335`).
6. **Cache design.** The cache key ignores worktree content for the default mode, config and tool version. The IR disk cache is write-only. The final cache and the LLM step interact inconsistently. There is no gitignore handling for `.diffcore/`.
7. **Eval and test infrastructure inside the product crate.** `eval/` (~5.5k lines) is compiled into the library. `git.rs` has 83 tests in the same file. Production types such as `RefinementResult` are said to live "in the Tauri crate, not core" (`cache.rs:~207`), so core exposes raw-JSON cache APIs because of a layering leak.
8. **Config and secrets handling.** `LlmConfig.key` stores plaintext and is persisted by `save_global`. A repo-local `provider` and `key` can steer a repo-controlled agent run. Config is split across `.diffcore.toml`, the global file, CLI flags and env vars, with ad-hoc merging (`apply_global_llm_defaults`). `config.rs` is 1461 lines mainly because 940 are tests, so it is not a god-module in production code. The env-var test mismatch is a real defect (section 3).
9. **Weak ranking.** Centrality is a constant 0.5, `has_db_migration` is hard-wired false, and `uncertainty` is a two-value constant. `symbols_changed` is never populated. The "semantic" review order is path keywords plus line count.
10. **Large files with mixed concerns.** `query_engine.rs` 2859, `git.rs` 2758, `refinement.rs` 2735, `ir.rs` 2427, `entrypoint/mod.rs` 2335, `llm/mod.rs` 2023 (JSON extraction, CLI binary discovery, key handling and the provider factory in one file). Error handling is inconsistent: `thiserror` enums in some modules, `Result&lt;_, String&gt;` in `session.rs` and `manifest.rs`, and `Box&lt;dyn Error&gt;` in the CLI.

## 9. CLI surface (`diffcore`, binary from `diffcore-cli`)

- **Subcommands** (`main.rs:44-64`):
  - `analyze`: `--base`, `--head`, `--range`, `--staged`, `--unstaged`, `--include-uncommitted`, `--no-include-uncommitted`, `-o/--output`, `--annotate`, `--refine`, `--refine-model`, `--no-cache`, `--repo`.
  - `launch`: opens a group's files in an external diff tool (`--tool bcompare|meld|kdiff3|code|opendiff`, `--group`, `--input`, `--repo`).
  - `eval`: `--fixture`, `--manifest`, `--format text|json|html`, `--min-score`, `--history-file`.
  - `lint-goldens`: `--manifest`, `--min-coverage`.
  - `export-groups` and `import-groups`: round-trip editable `GroupsManifest` JSON (`-i`, `-o`, `--repo`, `--base main`).
  - `list-models`: `--provider`, `--refresh` (24 h cache).
  - `embed-diff`: only with the `embeddings` feature.
- **Output:** JSON `AnalysisOutput` to stdout or file (pretty-printed via `output::write_json`). Logging goes to stderr through `env_logger`. `eval` has text/json/html formats.
- **LLM-consumer suitability:**
  - `analyze` (JSON) and the `export-groups` / `import-groups` loop (agent edits groups, re-imports) are the usable pieces.
  - The JSON has no entity/symbol data, no diff hunks and no graph, so it is a thin grouping manifest.
  - Refinement and annotation print status through `eprintln!` (plain text) and failures are warn-and-continue, so an agent can't tell from the exit code whether the LLM step ran.
  - `eval`, `lint-goldens` and `embed-diff` are maintainer tools; `launch` is for humans.

## Rework implications (my judgement)

- First, pick one extraction path. The `.scm` QueryEngine plus IR path is the only one with language breadth, and sem-core's entity extraction is an alternative. Delete the legacy `ast::parse_*` after switching.
- Add a single `core::analyze()` and make the CLI and server thin callers.
- Build the graph over the whole repo, or sem's `EntityGraph` with `build_incremental`, with edges that carry weight and call-site data. Then project it to file, module and symbol levels.
- Fix the cache key to include worktree content, config and version.
- Move eval and fixtures out of the library crate.
- Remove the repo-local `provider`/`key` overrides, and sandbox the Claude CLI like Codex's.</result>
